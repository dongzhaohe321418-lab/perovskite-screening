# S2 campaign 3 (C3): operating decisions, recorded before C3 starts (2026-11-07)

This note is committed before any C3 start that can run production (O25) and before any C3 value exists. It is committed on 2026-11-07, while C2 runs, so it also precedes the C3 runner. It records the analyst's decisions on how C3, the A1 production campaign of `S2_PLAN.md` §12 on the eight production hosts, is operated and how its results are treated. No C2 value was read for it. Where the code leaves a choice to the operator, it fixes that choice in advance.

**Rules changed.** The note departs from one rule of `S2_PLAN.md`, in one case only: the §13 limit of two reruns, for an attempt that the code starts beyond it at tally two or more (AM-C3-2). It departs from two readings of `STAGE0.md`, N-F13 (AM-C3-1) and N-D5 (AM-C3-3). Each amendment is dated and gives its reason (section 3). D-C3-11 and D-C3-7 state readings of §13 and §17, not amendments. Section 1 reads §16's "before any C3 job" as before any job that costs node-hours or yields a value. Other decisions add operating conditions (for example D-C3-2, D-C3-5, D-C3-8, D-C3-14) and remove no rule of `S2_PLAN.md` [I].

**Basis.** An operator runbook drafted from the code was reviewed through three adversarial lenses (47 findings, none rejected) and a completeness critique (14 operational defects, all accepted; no blinding defect). The analyst decided its 27 open items on 2026-11-07, under the PI's delegation of 2026-11-03, with four addenda after checks against the code. The runbook and its review record are private.

Labels: [I] marks the analyst's inference or arithmetic; [UNVERIFIED], what only the node can settle.

## 1. What C3 runs

- **Commit.** C3 runs at the S2 campaign commit `8bff03e`, with no redeployment, or at the new commit of a `c2/STEP0_FIX` that C2 accepted (D-C3-17). The runner accepts no other HEAD in C3: STEP0_FIX applies only in C2 [50:2363-2373], `c1/NODE_FIX` is refused outside C1 [50:2390-2391], and any other HEAD is a STOP [50:2377].
- **Preconditions.** C3 starts only if C2 is done and the C1 n rule was applied [50:2477-2487]. After K2 fail, step-0 fail_final or K3 a1_only, C3 runs, C4 does not, and S2 reports the A1 tier only (§11; [49:648-653]). After K3 fail_replan, C3 records not_run and runs no job [50:2482-2483, 4108-4112].
- **Hosts.** The n = 8 production list: m06, m02, m16, m12, m32, m26, m22, m23 (§3; [50:1331-1341]). Cs and Cl run at the default pose. Ca was removed by G1 (`C1_RESULT.md` §§3.1, 3.4).
- **Graph.** 1589 jobs, by the graph preview of `scripts/50` with a state that holds the C1 decisions [50:7273-7282] [I]. The runner asserts these counts at every graph build [50:1405-1462, 2511-2513]. They are 8 host relaxations (MACE, whole cell, three FIRE stages of up to 10 000 steps [46:148, 1253]), 536 frozen MACE relaxations (per host 19 V⁺_R and 48 dopant cells), 544 single points (68 per host), 496 geometry jobs (152 regions, 152 vacancy starts, 192 pair builds), 3 checks (UPF files, node scripts, MACE environment and model [50:1351-1353]) and 2 gates.
  - **Phases.** check, pre, mace, qe, gate, strictly in order [50:680, 2616-2619]. MACE never runs beside pw.x (N-7, [50:767]).
- **Gates.** There is no step-0, K2 or K3 gate.
  - **`projection@c3`** runs after the three checks [50:680, 1351-1354] and before any geometry, MACE or single-point job. The checks cost no node-hours, yield no value and depend on no cut [I]. It recomputes P of §16 from H_spent, the completed C2 A2 timings and the C1 single-point and MACE walls [49:1317-1349, 1429-1446]. Cuts apply while P > 520 node-h and are never undone [49:764-782]. Cuts 5-7 cannot apply at n = 8 with default poses [49:741-746], and cuts 1-4 and 8 act on C4 only, so no cut changes C3. A cut is reported and C3 takes no action; cut 2 or later leaves df_δ ≤ 2, so C4 could validate no class (`C1_RESULT.md` §5a; O15).
  - **`c3_complete`** runs at the end. It reads every C3 single point in status mode, and its decision is true iff none reads pending or running [49:1356-1366] (D-C3-4).
- **Limits fixed by the code.**
  - At most 10 MACE relaxations run at once, at 6 threads each [46:149; 50:2653-2655].
  - Single points run one at a time in the node's QE queue, with two published ahead [50:675, 3155-3169]. An output without JOB DONE is resubmitted once with the identical input, and a second failure makes it missing [queue:11-15]. A JOB DONE output whose SCF did not converge is missing and not rerun [47:1329-1332] (§12).
- **Cost [I] (O16).** About 66-82 node-h, central about 68, before interruptions and the waits of D-C3-10: 57.9-61.1 node-h for 544 single points at 6.39 min (C1's single-point phase wall over its 129 single points, `C1_RESULT.md` §1 [I]) or 6.74 min (§16); 6.2-17.9 node-h for 536 frozen MACE relaxations at 0.7-2 min of node time each (C1's MACE phase less its host wave, or the plan's unit cost); and a host wave of 1.6-3.3 h (§16). The estimate is updated after the MACE phase and after the first 50 single points.
- **Hard cap.** It stays at 520 node-h (§16; [49:785-788]).
  - H_spent was 20.56 node-h after C1 (`C1_RESULT.md` §1). With C2 (40-86 node-h, `C2_OPERATIONS.md` §1) and C3 (66-82 node-h) it is about 127-189 node-h at C3's end, or about 225 if every C2 relaxation reaches its cap [I]. Interruptions add to it.
  - A refusal persists across starts [50:3039-3045]. Every MACE job and single point not yet started then becomes not_started_cap. Geometry jobs and gates still run (N-F14; [50:2525-2531]).

## 2. Decisions

- **D-C3-1 (publication of the C3 archive; O1).** The C3 archive is not committed to this repository before the one evaluation. It is written to the private record and verified there.
  - **Reason.** It holds every raw production output and every MACE record with its `E_mace_eV` [50:4256-4327; 46:1257, 1264, 1316].
  - **Exception (critique finding 11).** A not_run C3 holds no production output (section 1). It is archived to `results/objective2/s2/c3` and committed with a dated note; the one evaluation then needs its `c3/campaign.json` in the archive root [48:1273-1277].
  - **Backup copy (critique finding 14).** A read-only copy of the node's C3 trees may be pulled into the private record after the host wave, then daily. It is never opened or used for the archive, each pull ends before the final pull, and the copy is used only if the node's disk is lost, by the analyst's decision.
- **D-C3-2 (no production start of C3 in the boot that ends C2; O2).** A C3 start that can run production is made in a new boot, after C2 has been pulled, archived, committed and verified (D-C2-6, D-C2-7) and its decisions read from the archive.
  - The code would allow a start in C2's last boot [50:2477-2487]. Against it: the plan stops the node after each campaign (§17 item 5); C3 must not follow a C2 that D-C2-6 has not accepted; and a shared boot would need its node-hours split (D-C2-10).
  - **Not_run starts.** The rule does not cover the not_run start that `STAGE0.md` requires after K3 fail_replan (§7, R5-C24-1). It runs no job and writes no boot record [50:2482-2483, 4108-4117], so the first and third reasons do not apply. For the second, a K3 difference that D-C2-6 finds later is a stop for the analyst, and a not_run c3 holds no output to undo [I]. It is made in the boot that ends C2 or, if missed, in its own boot with a manual ledger entry (O18). The only other not_run route, an Sr gate-N failure [50:2479-2480], cannot arise: Sr passed gate N (`C1_RESULT.md` §3.2).
- **D-C3-3 (STOPs that need a code or data fix; O3).** Any C3 STOP whose remedy needs a code or data change ends in "stop and re-plan" by a dated amendment, as D-C2-3 did for C2, with the end procedure of D-C3-12. The runner accepts no commit change in C3 (section 1), so a fix route would need a new commit. Keeping `scripts/` and `ehpc/` unchanged during S2 is the analyst's choice, not a plan rule: it keeps the campaign commit's reviewed code for the one evaluation. For the analysis script, §17 item 6 fixes it before C3; after that only a rerun after a code error changes it.
- **D-C3-4 (`c3_complete` with skipped single points; O4).** Accepted as the code reads it.
  - **Code.** A skipped single point (its cell missing or its pair rejected) and one refused by the hard cap have no job directory [50:2525-2531, 3093-3100], so their status read returns pending [47:1313-1315]. The runner passes all 544 labels to the gate [50:2722-2723]. So the decision is false whenever a cell is missing or a pair rejected, though every job has ended. No code reads it [I], and §12 asks only that completeness be recorded.
  - **Split test.** The C3 note reports the decision with `result.counts` and this split against `completeness.json`: complete = done; missing = missing; pending = skipped + not_started_cap (an absent key counts 0); no running. A false decision with this split is not a defect; any other split is a stop for the analyst.
- **D-C3-5 (reclaims during the host wave; O5).**
  - **Risk [I].** The eight hosts start together [50:1359-1363], so one reclaim in the 1.6-3.3 h host wave interrupts all of them. A host cut at tally two or more is missing (D-C3-11; AM-C3-2 excepted), and its 67 cells and 68 single points are skipped [50:1096-1117, 2558-2566]. Three host-wave reclaims would leave C3 with no production, S2's largest data-loss risk. An interruption is recorded only at the next relaunch [50:2893-2919].
  - **Rule in force (b).** Every counted interruption is reported to the analyst within the hour. Before any relaunch that would start any host's last attempt under its rerun tally (the attempt at tally two; D-C3-11), the operator stops for the analyst. The analyst decides between a relaunch on spot, as the code allows; a non-spot boot, by a dated decision with the runbook re-issued for it; and stopping C3 and re-planning by an amendment.
  - **Non-spot boot.** The PI is asked whether the host wave can run on a non-spot boot of the same node, and at what cost [UNVERIFIED]; the answer is recorded before the first C3 boot. A non-spot host wave is not automatic: if the PI agrees, a dated decision before that boot fixes the boot type and gives the runbook its procedure. Otherwise every host wave runs on spot under rule (b).
  - **No idle node during a hold (critique finding 2).** A boot to read the state first removes a stale keep-alive file, which would keep the node up (§16; the code removes it only at a refused relaunch [relaunch:12-13, 19-29]). It then only reads the state. Without a decision within about 15 min the node is stopped, and that boot gets a manual ledger entry at the next S2 boot (`STAGE0.md` §8 item 10).
- **D-C3-6 (attempts ended by the shutdown at a reclaim; O6).**
  - **Gap [UNVERIFIED].** At a shutdown, a running MACE attempt's wrapper may record exit 143 [50:1551-1554]; the relaunch then STOPs for a human (N-9) instead of counting an interruption [50:2917-2918]. A shutdown during check:mace can leave a failed check record and a STOP, since the checks have no shutdown test [50:1766-1770, 2700-2702, 2737-2740].
  - **Decision.** An exit 143, or a check:mace record with load exit -15 or -9, whose time matches the end of the old boot is the reclaim. For a MACE attempt the operator writes RESOLVE 'rerun' with a note that begins "shutdown exit 143", or 'missing' if the cell's tally is two or more; that rerun is in the tally (D-C3-11). For check:mace the runner is started again: a failed check record is pending [50:2572-2574].
  - **One event, several attempts (critique finding 5).**
    - Each ended attempt that the code does not count gives its own STOP at the next start, before anything is scheduled [50:2915-2918, 4172-4196].
    - After the first such STOP, the operator lists the ended attempts by exit code and time only. The list marks every attempt that the code counts itself (an earlier boot's attempt with no exit code or exit 137, and an OOM kill [50:2913-2914, 2919]), which gets no decided RESOLVE. Its rerun-limit RESOLVE (D-C3-11) is written before the first start after the boot, since that start leaves a later one unread [50:2893-2894, 2984-2985].
    - One dated analyst decision records that the listed attempts ended in the same event (the same exit code within the last minute of the old boot, or the same exception type). The decided RESOLVE is then written for each, and the runner is started once (AM-C3-3).
- **D-C3-7 (what the operator reads; O9).** Until the one evaluation, the operator reads decisions and counts. C3 outputs are read only for completeness, validity and timings. The timings are walls, which the code reads for the hard cap (`relax.wall_s` only [50:2312-2332]), and FIRE step counts, which during C3 are read only for the hang bound of D-C3-10. Neither holds an energy, nor can they be combined into a binding energy at the resolution of the classes [I]. This is a reading of §17, which names completeness, validity and the end rule. No E_b, Y_h or δ of a production host is computed, by DFT or by zero-shot MACE.
  - **Cell records.** A C3 cell record is opened only through the blinded loader of `scripts/46`, which removes every `E_mace_eV` [46:346-358]. Of it only these fields are read: `member`, `cell_kind`, `site`, `token`, `leg`, `n_free` and `n_fixed`; `validity.valid` and `validity.failed`; `relax.steps`, `relax.converged` and `relax.wall_s`. Never read are `relax.stages`, which holds energies [46:1256-1257], the force fields (`relax.fmax_final_free_eVA`, `validity.checks`) and the FIRE trace `fire.log` [46:1309-1310]; a record is never printed whole.
  - **Attempts.** The attempt lists, exit-code and pid files and missing markers are read in full, and whether a RESOLVE exists. Of a failed attempt's log only the exception type is read, never its message, which for a frozen relaxation can carry a force [46:1305].
  - **Pair records.** `status`, `rejection.exception` and `rejection.leg`.
  - **Gate files.** They hold no energy [I]. Of `projection@c3`: the decision and the node-hour and count fields of `result` (`P_initial_h`, `cuts`, `inputs`, `a2_completed`, `work_after`) [49:1442-1446]. Of `c3_complete`: the decision, `result.counts`, `result.n` and `result.missing` (label and reason) [49:1356-1366].
  - **Single-point outputs.** Only file names, their times and the three header lines that name the program version, the MPI process count and the input file (no energy). The code reads outputs in status mode [47:1271-1333].
  - **Readers of C3 outputs (critique finding 9).**
    - The runner. Its QE-output reads are listed in `c3/runner_reads.jsonl` [50:1989-2003]. It opens cell records only through the blinded loader [50:2866-2885, 2325-2330].
    - The status command.
    - The two node gates, run by `scripts/49`, which list their reads in the gate file's `opened` and `inputs_opened` fields [49:917-919, 1456, 1521]: the C3 single points in mode status (`c3_complete` [49:944-955, 1356-1366]); for `projection@c3`, the C1 single points in mode status, the C1 MACE records in mode records and the C2 A2 records in mode files [49:969-994, 1257-1265, 1321, 1336, 1342, 1432]. Of each entry only the label, the file name and the mode are read; a label is not a value. Any other mode is a defect to report.
    - The pull, the backup copy and the archive builder of `scripts/50`, which copy, hygiene-check and archive the files and compute nothing [50:4240-4335].
    - At the end, the verify step of `scripts/49` and the field comparator of D-C2-10.
    - Any other reader is a defect to report.
  - The C1 and C2 rules stay in force (D-C2-5, D-C2-10).
- **D-C3-8 (the MACE environment; O10).**
  - **Code.** `check:mace` pins mace-torch 0.3.16 and the model's sha256 [46:150-152, 1687-1722] but no version of torch, e3nn, ase or numpy; §5 asks only that these four be recorded per campaign. The C1 MACE check record holds the versions of mace, torch, e3nn, ase, numpy and Python [46:402-406, 1719-1721].
  - **Decision.** Before the launch and every relaunch (D-C3-17), the node's installed versions are compared with the C1 record. A torch or e3nn version that differs from C1 blocks the start until the C1 versions are restored. Python, ase and numpy are recorded only; scipy, in neither MACE check record, is recorded for C3 without comparison.
  - **Reason [I].** torch and e3nn set the potential's numerics; a change would make production geometries differ from those of the C1 pilots.
- **D-C3-9 (an invalid host; O11).** Accepted as the code reads it. A host whose relaxation is invalid still runs all its cells: the runner reads no validity (N-F12, [50:749-751]), and `scripts/48` applies "missing for every dopant" later (§5). Such a host, or any pattern of failed checks, is reported to the analyst at once and not acted on; no cell is rerun with other settings (§5).
- **D-C3-10 (a MACE attempt at its wall limit; O21).**
  - **Code.** A MACE attempt beyond 12 h (host) or 3 h (frozen) is a STOP that kills nothing [50:669, 2921-2927], and the drain that follows has no wall test [50:4137-4162]. A host's 30 000 FIRE steps take about 20 h at 2.4 s per step [I, from the host walls of §16]; a frozen cell runs up to 10 000 steps [46:147].
  - **Decision.** An attempt that is still computing at its limit is let finish in the drain (AM-C3-1). It then writes its record, valid or invalid, and counts as done at the next start [50:2878-2886]. Only a hang is ended by the operator and resolved as D-C3-11 says.
  - **Upper bound (critique finding 4).** An attempt whose elapsed wall exceeds 1.25 times its step-cap time is treated as a hang, whatever its CPU time. That time is 30 000 (host) or 10 000 (frozen cell) times the median seconds per step of the completed C3 records of that kind (`relax.wall_s` / `relax.steps`), or 2.4 s per step before any exists [I].
  - **Bookkeeping.** Every wait is logged in node-hours; the analyst re-decides when their sum passes 10 node-h or more than three frozen cells reach the limit.
  - **Watch (critique finding 3).** After any STOP in the MACE phase while a MACE child runs, and after a STOP for a hung single point (above all when its drain waits for other work), the watcher stays and reports the end of the drain. The resume then follows within about 45 min, before the idle self-stop of 60 min (§16).
  - **Reason.** Ending a computing attempt turns a cell that §5 would record into an identical rerun at the same cost, or into a missing cell (for a host, see D-C3-5). §12 warns that treating dopant-specific failures as missing at random biases Y_h towards zero.
- **D-C3-11 (the rerun tally of a MACE cell; O6, O22).**
  - **Rule (a reading of §13).** §13 allows a MACE cell at most two reruns after a reclaim, node loss, OOM or wall time. A cell's tally is the interruptions that the code counts (reclaim, node loss, OOM), plus the operator's reruns after a wall-time STOP (D-C3-10) or a shutdown exit 143 (D-C3-6), which the code records as not counted [50:2962-2965]. At a third counted interruption the code makes the cell missing [50:661, 2969-2971, 2984, 2989-2991]. An operator's rerun after an exception is not in the tally, as D-S0-11 (b) and N-F33 decided: it follows a diagnosed cause, needs a human and cannot select on a value. An exit 143 at a shutdown is the reclaim and a wall-limit STOP is wall time, both §13 causes; neither is an exception, so D-S0-11 (b) is not touched. At tally two or more, the next end by a §13 cause makes the cell missing; AM-C3-2 is the one exception.
  - **Operator's count.** The note of an operator rerun in the tally begins "wall time" or "shutdown exit 143". The operator writes a RESOLVE as word, date and note; the code records the text after the word, prefixed 'operator: ' and cut at 120 characters [50:2950-2953, 2965]. The tally test is whether the note after the date begins with either phrase, ignoring leading spaces and case.
    - At a wall-time or exit-143 STOP of a cell at tally two or more, the operator writes RESOLVE 'missing', never 'rerun', with a note that names the cause.
    - Before every relaunch in the MACE phase, the operator lists each cell whose last attempt ended without a record, with its tally. A cut attempt that the code counts but has not yet recorded, at tally two or more while the code's own count is below two, gets RESOLVE 'missing' with the note "rerun limit (D-C3-11, O22): two reruns used; last attempt cut by the reclaim" (or "by node loss", or "by an OOM kill"). The code reads it before the exit status and records the cell missing [50:2906-2908, 2959-2961] (AM-C3-3); otherwise it would start a further attempt [50:2989-2991]. If such a RESOLVE was missed, AM-C3-2 applies to the further attempt.
    - The code reruns an OOM kill in the running boot while its own count allows [50:2913-2914, 2989-2991]; at tally two or more, AM-C3-2 applies.
- **D-C3-12 (a final C3 STOP; O23).**
  - **Code.** A final STOP (D-C3-3) leaves the status stopped [50:2248] and no `state_end.json`, which only the normal end writes [50:2285-2297], so `scripts/48` refuses the one evaluation, whether C4 is planned or not [48:1263-1281].
  - **End procedure.** The node trees are pulled and archived into the private record (D-C3-1), and the gates that ran are verified (D-C3-17). No evaluation follows; the STOP is reported. Without a C3 single-point tree on the node [50:3121-3124], that part of the pull and its check are skipped (critique finding 7).
  - **Re-plan.** The amendment states how S2 ends: at the A1 tier from the existing records, which needs a dated change of `scripts/48` with its amendment (N-F29) and is itself a departure from §17 item 6 [I]; or by a C3 restarted under a new commit and campaign record.
- **D-C3-13 (this note; O25).** O25 asks for a commit before any C3 start that can run production; this note is committed earlier (opening paragraph). It holds decisions only: no S2 energy or result value, no node name, address or identifier, and no local path. The repository-state check before the first C3 boot is repeated after this commit.
- **D-C3-14 (the node is reserved for C3; O26).** The node is reserved for C3 from its first boot to the stop after the pull, about three days. The PI tells every other line of work that uses the node before that boot.
  - **Reason.** Other work shares the chain script's global lock [chain:6]. A foreign QE queue would delay the S2 single points silently or raise the hung-run STOP [50:2929-2937, 3090-3091]; a foreign pw.x in the MACE phase would share the cores with up to 60 MACE threads. The C3 code detects neither [50:1818-1819, 2079-2085].
  - **Check.** At every progress reading the operator checks for foreign work. Foreign QE work is a pw.x, QE queue or chain outside the C3 trees. Foreign MACE work is a python or MACE process whose working directory is outside the S2 trees (checkout and work tree) and whose CPU time grows between two readings. The S2 runner and everything it starts, the spot poller, gates and geometry jobs included, run inside them [camp:15, 24; 50:1708-1709, 1716-1719, 1748-1750, 2102-2107, 3011]. Selection is by process name, so a program started under another name escapes it [I]. On any foreign work the operator reports at once, stops for the analyst (O26) and kills nothing. A published S2 input without output for 15 min is a sign only while no S2 pw.x runs, since one S2 single point may run for about an hour and the next waits for it [47:199; queue:10-20] [I] (critique finding 1).
  - **Relaunch refusal (critique finding 12).** The relaunch script refuses while any pw.x, QE queue, chain or run_qe.sh lives [relaunch:32-36]; the operator retries only if each is their own command, else treats it as foreign work.
  - **One operating session (critique finding 10).** One session runs node commands at a time. At a handover the outgoing session records every open STOP, drain, hold, RESOLVE and pending decision privately, stops its watcher and sends no further node command; the successor reads that record first.
- **D-C3-15 (the D3(BJ) amendment; O27).** D-S0-4 requires a dated amendment on the D3(BJ) row before the one evaluation (`STAGE0.md` §9), which may follow C3 at once when C4 is not planned [48:1269-1279]. The amendment was written on 2026-11-07, before C3; it needs no C3 value and is committed before the one evaluation.
  - It takes the second branch of D-S0-4, that the row is not reported, by choice, not by necessity. The reason is the amendment's: the one evaluation cannot be repeated except after a code error, so unreviewed row code in it would put the primary PBE result at risk.
  - It pre-registers a separate study after the one evaluation: a fixed-geometry D3(BJ) energy on the archived geometry of each PBE energy of every evaluated cell (MACE-relaxed for A1 and the A2 start, PBE-relaxed for the final A2 energy). The study reports the shift of each E_b and whether any class would change; it changes no S2 decision.
- **D-C3-16 (rules carried over from C2; O17).**
  - **D-C2-4 (operator notes).** Every operator note (RESOLVE, a manual ledger entry) passes the hygiene check of `scripts/46` [46:315-325] on the laptop before it is written on the node, since these notes enter guarded JSON [50:1942-1943, 2157-2161, 2957-2958, 2986-2988, 4260-4262; 46:336-342]. A failing ledger note would stop the runner at the next ledger snapshot [I].
  - **D-C2-8 (disk), extended.** Nothing in the node's C1, C2 or C3 work and single-point trees is deleted before the one evaluation. C4 reads the C2 walls from the node [50:2312-2324]. Below 50 GB free on the data disk, the operator stops for the analyst.

## 3. Dated amendments (2026-11-07, for C3)

§16 requires every deviation to be written as a dated amendment before the affected values are read. Each amendment below was written before any C3 value existed, applies to C3 only and changes no code.

- **AM-C3-1 (`STAGE0.md` N-F13: a MACE attempt at its wall limit).** N-F13 (Appendix A) reads the wall-limit STOP as "the operator ends the process and resolves with RESOLVE" [50:752-754]. In C3 an attempt that still computes at its limit is let finish; only a hang, bounded as D-C3-10 says, is ended and resolved. Reason: that of D-C3-10. The STOP kills nothing [50:2921-2927], so the code is unchanged.
- **AM-C3-2 (§13: an attempt that the code starts beyond the limit).** At tally two or more (D-C3-11), the code can still start an attempt, which is then beyond the §13 limit whatever its number. There are two routes. After a same-boot OOM kill, which it counts, it starts the next attempt at once or later [50:2913-2914, 2989-2991, 4179-4192]. After a missed rerun-limit RESOLVE (D-C3-11), it reruns a cut that it counts [50:2919, 2973-2991]. Both need the code's own count below two, so this can happen at most twice per cell: at its own third counted interruption the code makes the cell missing and starts nothing [50:2989-2991], and no departure arises. AM-C3-3 allows no advance RESOLVE: it would stay unread beside a record if the attempt succeeds [50:2878-2886], and would turn an exception (N-9) into a missing cell without a STOP [50:2906-2908, 2915-2916]. Each such attempt is let finish and kept; the operator kills nothing and reports it at once, and the C3 note reports it as a departure from §13. Reason: it is an identical rerun, started by the code before any output is read, so it cannot select on a value.
- **AM-C3-3 (`STAGE0.md` N-D5: a RESOLVE for a job with no open STOP).** N-D5 resolves a STOP for one job by a RESOLVE in that job's directory. In C3 the operator may also write one for a job with no open STOP, in two cases only: the listed attempts of one event (D-C3-6), whose own STOPs would follow one per start, and the rerun-limit 'missing' of D-C3-11, for which the code raises no STOP and would start a further attempt. Reason: the code reads a RESOLVE before the exit status of an ended attempt and accepts both words [50:2906-2908, 2946-2966]. Without it, one event costs a STOP and restart per attempt, and a cell could exceed its tally.
